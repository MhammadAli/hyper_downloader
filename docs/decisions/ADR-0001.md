# ADR-0001: Foundational Architecture — Modular Rust Engine, FRB v2 Boundary, Android UIDT Transfers, and Official YouTube API Compliance

- **Status:** Partially Superseded by [ADR-0002](./ADR-0002.md) (Decision 4 superseded by `MediaExtractorBackend` + `yt-dlp`)
- **Date:** 2026-11-18
- **Decision Drivers:** Cross-platform parity (Windows Desktop + Android API 26–36), byte-level HTTP resume integrity, resilience against Android background process termination, strict YouTube Terms of Service compliance, and independent testability of the Rust download engine.

---

## Context

HyperDownload requires a single high-reliability download engine shared between a Flutter desktop client (Windows) and mobile client (Android), paired with platform-specific integrations for Android intents, notifications, storage, and background data transfers. We must select:
1. How to structure the monorepo and Rust crates so provider adapters never leak into core download execution.
2. How Flutter communicates with Rust without passing large media buffers or coupling business logic to widgets.
3. How Android guarantees long-running transfers survive backgrounding and OS process termination policies introduced in Android 14 and Android 15.
4. How YouTube integration behaves cleanly under official APIs and Terms of Service without resorting to unofficial scraping or DRM/signature bypasses.

---

## Decisions

### Decision 1: Modular Rust Workspace with Isolated `engine_ffi`, `providers/direct_http`, and `test_server`
We adopt the modular workspace structure (`apps/client` + `rust/crates/*`) and introduce three focused crates:
- `engine_ffi`: Isolates `flutter_rust_bridge` v2.13.0 glue and the Tokio runtime from pure domain crates (`download_core`, `download_queue`, `persistence`).
- `providers/direct_http`: Models ordinary HTTP/HTTPS downloads as an explicit `MediaProvider`, keeping `download_queue` completely free of URL inspection logic.
- `test_server`: Embeds a local Axum HTTP test server inside the workspace so every edge case (non-Range 200 responses, dropped TCP streams, mutated ETags, chunked unknown lengths, redirects, 403/404/500) is tested deterministically offline.

### Decision 2: `flutter_rust_bridge` v2 (`2.13.0`) + Cargokit + Bundled `rusqlite` State Ownership
- **Rust owns persistence and I/O:** All SQLite state (`rusqlite` with `bundled` feature and WAL mode), HTTP streaming (`reqwest` with `rustls-tls`), `.part` file writes, and byte-range checks live in Rust.
- **Zero-buffer FFI:** Dart receives only metadata structs, SQLite job snapshots, and throttled (100–250 ms) `StreamSink<EngineEvent>` progress diffs. Media payloads never cross FFI.
- **Testability:** Flutter Blocs depend on a thin abstract `DownloadEngineClient` repository wrapping generated FRB functions, making widget and `bloc_test` suites fast and mockable.

### Decision 3: Android Background Transfers via `JobScheduler` UIDT (API 34+) and `WorkManager` / `dataSync` Fallback (API 26–33)
- On Android 14 (API 34) and Android 15/16 (API 35/36), `dataSync` foreground services are subject to strict aggregate runtime limits (6 hours within 24 hours on Android 15). Therefore, HyperDownload uses **User-Initiated Data Transfer (UIDT)** jobs (`JobInfo.Builder.setUserInitiated(true)`) via `HyperDownloadJobService : JobService` with `RUN_USER_INITIATED_JOBS` and `POST_NOTIFICATIONS`.
- On Android 8.0–13 (API 26–33), HyperDownload falls back to `WorkManager` `CoroutineWorker` running as a foreground service (`FOREGROUND_SERVICE_TYPE_DATA_SYNC`).
- **Process Lifecycle Checkpoint:** `JobService.onStopJob()` synchronously triggers Rust `flush_and_checkpoint_for_suspend()`, syncing active `.part` buffers to disk and saving exact `(bytes_received, etag, last_modified)` checkpoints in SQLite before returning.

### Decision 4: Official YouTube Data API v3 Integration with Explicit Metadata vs. Download Separation *(Superseded by [ADR-0002](./ADR-0002.md))*
> **Superseded Note:** Decision 4 has been superseded by [ADR-0002](./ADR-0002.md), which introduces the `MediaExtractorBackend` abstraction backed by `yt-dlp` for URL-based media format discovery, stream downloading, FFmpeg muxing, and playlist inspection across publicly accessible and authorized media sources.

- `providers/youtube_metadata` connects **exclusively** to official **YouTube Data API v3** endpoints (`videos.list`, `playlists.list`, `playlistItems.list`, `channels.list`, `captions.list`, `captions.download`).
- Because YouTube Terms of Service forbid downloading content unless expressly authorized by the service and YouTube Data API v3 does not expose downloadable video/audio stream URLs:
  - Public YouTube videos and playlists are inspected truthfully and tagged `MetadataOnlyPlatformRestricted` with zero fabricated download formats.
  - Authenticated video owners connecting OAuth 2.0 gain official inspection of `fileDetails` (when `processingDetails.fileAvailability == "available"`) and authorized caption downloads via `captions.download`.
- Unofficial watch-page scraping, player cipher decryption, and client impersonation are permanently out of scope.

## Consequences

### Positive
- Pure Rust engine (`download_core`, `download_queue`, `persistence`, `providers/*`) compiles and runs full integration tests via `cargo test` without requiring Flutter, Android emulator, or Visual Studio runner hooks.
- Byte-range checks and SQLite WAL checkpoints prevent partial-file corruption across pauses, network drops, non-Range servers, and Android OS preemption.
- Full compliance with Google Play / Android 14–16 background execution rules and YouTube API Terms of Service.

### Negative & Mitigations
- **Developer Toolchain Requirements:** Windows compilation and FRB v2 codegen require Rust (`x86_64-pc-windows-msvc` + Android NDK targets), Visual Studio 2022 C++ Build Tools, and LLVM/Clang (`libclang`). *Mitigation:* Documented exact setup steps in `docs/DEVELOPMENT_GUIDE.md`.
- **Two Native Android Paths (API 34+ vs 26–33):** Maintaining UIDT `JobService` alongside a `WorkManager` fallback adds moderate Kotlin code. *Mitigation:* Both invoke the exact same Rust `download_queue` lifecycle/checkpoint APIs, keeping download behavior identical.
- **Public YouTube Videos Are Not Downloadable:** Users expecting a generic YouTube video ripper will see `Metadata Only`. *Mitigation:* Make the distinction transparent in `PRODUCT_SPEC.md` and the Media Inspection UI, while supporting full authorized HTTP downloads and owner YouTube captions.
